# EBT 三组检索实验结果

2026 年 11 月 24 日运行。对 39 条有参考链接的需求逐条评分，候选库包含全部 25 条用例，参考矩阵共 51 条链接。三个方法使用相同的清洗文本和评分代码。

| 方法 | Recall@5 | Recall@10 | MAP | 每需求中位延迟 |
| --- | ---: | ---: | ---: | ---: |
| BM25 | 85.04% | 91.03% | 0.6946 | 0.05 ms |
| MiniLM 语义检索 | 95.73% | 98.72% | 0.7954 | 4.79 ms |
| MiniLM + DeepSeek 重排 | 97.01% | 98.72% | 0.8941 | 2.22 s |

语义检索相对 BM25 的 Recall@5 增加 10.68 个百分点。DeepSeek 重排在此基础上再增加 **1.28 个百分点**，39 条需求中有 1 条改善、38 条持平。MAP 增加 **0.0987**，其中 12 条需求的 AP 改善、26 条持平、1 条下降。重排的前 10 项集合固定，因此两组的 Recall@10 相同。这批候选能达到的宏平均 Recall@5 上限为 98.29%。

延迟从候选索引建好后计时。语义检索含查询编码与排序，重排还含 API 往返、校验及必要时的重试。两组基线的延迟不含模型初始化或候选索引构建。

## 逐需求案例

| 需求 | 参考用例与名次变化 | 解释 |
| --- | --- | --- |
| 137 | 164 从第 7 名升到第 2 名，Recall@5 从 0.5 升到 1.0 | 需求要求按接收顺序显示事件。用例 164 检查系统能否阻止乱序处理，模型给出 1 级关联并引用了具体限制。原先第 2 名的用例 161 聚焦发送通知，模型给出 0 级。 |
| 119 | 152 从第 3 名升到第 1 名，Recall@5 保持 1.0 | 用例步骤直接写明恢复模型到先前状态，模型把这一行为放在仅共享订阅管理器术语的用例之前。 |
| 106 | 143 从第 2 名升到第 1 名，144 留在第 11 名 | 144 在语义检索阶段未进入前 10，重排无法将其带进前 5。该需求的候选限制下 Recall@5 上限为 0.5。 |
| 111 | 149 和 150 各下降一位，AP 从 1.0 降到 0.5833 | 用例 161 升到第 1 名，其事件通知行为与需求有相似之处，但原文对象是受管理的订阅者，需求对象是受管理的制品。引文逐字匹配仍可能伴随语义判断错误。 |

本轮对这个英文项目的证据表明，重排更多地改善了参考用例在候选列表中的位置。前五项的增益集中在需求 137。样本来自一个项目，结果的跨项目稳定性尚待检验。

## API 用量

正式实验发起 40 次请求。需求 128 的首次响应未通过结构校验，重试后成功。39 条需求均完成重排，回退数为 0。390 项判断中有 3 项的正向引文校验失败，排序时按 0 级处理。

正式运行消耗 47,356 个输入 tokens，其中 6,016 个命中缓存，另有 16,844 个输出 tokens。按运行时段适用的闲时官网价格计算，正式实验约 ¥0.109。该金额根据响应中的用量估算，手写样例测试另计。 [DeepSeek 定价](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)
